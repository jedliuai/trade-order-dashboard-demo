# 精简客户四象限与手动汇率

## 做了什么

把默认演示库从 72 家客户压缩到 24 家，三个业务员各 8 家。默认财年和本月的四象限各有 2 家客户，经理汇总时各 6 家。客户改用短小、互不重复的虚构名称，避免气泡标签都截成同一个“DEMO 虚构客”。合同从 1200 份减到 168 份，联系单从 3000 条减到 313 条；仍保留历史业务、在制订单、批次、客户预存款、包装提醒和利润待计算样例。

汇率只保留月度手工输入、保存、删除，来源统一为 Manual，服务端拒绝自动来源。收款页的“自动查询汇率”也改成“使用手动维护的汇率”，避免误以为在联网抓取。当前月已经有明确标注为虚构的样例数值。

## 为什么做

之前的数据适合测试大列表，但不利于讲解：客户太多，回款和利润又高度同向，两个象限几乎空白。演示需要少而有代表性的业务情景，让观众能看清四类客户各自的含义。

## 值得记住

没有直接往图表塞坐标，也没有改客户分层和利润公式。四个象限来自真正关联的虚构订单、开票、回款和月度成本。跨 Python 种子和前端分析函数做了回归：当前财年、本月、元旦和闰日都能得到每个业务员八家客户、每个象限两家。

先检查原库再替换：18 类核心业务表与 2026-09-27 的原虚构生成器逐字段完全一致，三份原始备份也一致，没有发现真实业务混入。重建前另留一份本地 JSON 备份；重建后的所有表又与当天精简生成器完整比对。运行库和备份都不进入 Git。

旧的 72 客户大规模生成器没有删，改为容量测试显式调用；默认启动、重置及种子 JSON 都使用精简版。这样既保留测试覆盖，也不会下次重置又恢复成拥挤界面。

Edge 实际验证了八家客户的矩阵、四类客户排名、手动录入汇率及其 SQLite 持久化；没有浏览器错误或外部资源请求。测试用汇率随后恢复。自动验证包含 2 项脚本测试、299 项前端测试和 107 项 Python 测试，并通过 lint 和构建。

## 一句话亮点

客户少一点，故事更清楚：八家虚构客户撑起四个经营象限，连汇率也牢牢掌握在自己手里。
