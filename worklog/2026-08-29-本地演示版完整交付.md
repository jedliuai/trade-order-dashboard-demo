# 本地演示版完整交付

## 做了什么

把原订单驾驶舱整理成了一个全新的纯本地演示项目。前端继续保留合同、联系单、批次、发货、回款、开票、利润、分析、主数据、十类导出和 Telegram 汇报；数据层改成项目内的 Python HTTP 服务与 SQLite。预置了 72 个虚构客户、1200 份合同、3000 条联系单，以及能串起来的批次、发货、收款、发票、成本和汇率。还补齐了一键安装、开发启动、正式构建、本机启动、测试和 CI。

清理了旧云端数据库、NAS/APS 同步、Cloudflare、n8n、远程 worker、旧模板、截图、业务文档和旧部署配置。真实信息没有复制进演示版，运行数据库、备份与 Telegram 凭据也都由 Git 忽略。

## 为什么做

这个项目要能放心给别人演示，又不能把真实公司、客户、服务器、模板和历史数据带出去。只改几个人名不够，必须把存储、业务动作、导出、汇报和启动方式一起本地化，才能做到界面完整、数据丰富、操作真实，同时与原生产环境彻底断开。

## 值得记住的决策、坑和技术点

- 演示身份只用于业务员、经理、负责人的展示范围，不冒充生产级登录；服务始终只绑定 127.0.0.1。
- 财务规则没有因为“演示”而简化：利润仍需要实际开票、当月成本和汇率，缺项就显示待计算；归档仍要求足额回款和足额实际开票。
- 制剂实际发货必须已经入库，准备中的发货安排可以先占用数量；美元合同固定自营，人民币合同固定转口。这些原规则都做了事务级回归测试。
- 导出不能只做到“文件能打开”。十种 Excel/Word 都用真实筛选和通用模板生成，并专门防止公式注入、多币种误加、重复回款和逐项利润串行。
- Telegram 默认只预览，密钥只从本机 `.env.local` 读取；未配置或未明确确认时绝不发送。
- 大数据首次加载原先会反复解码整库，Edge 实测暴露了等待问题。改成一次 bootstrap 读取同一份角色快照后，只需一个主要数据请求，页面更快且避免拼到不同事务时点的数据。
- Windows 上 Vite 清空正在使用的 dist 会静默退出。正式构建现在先生成完整临时目录，再原子替换 dist，失败时保留上一版，既不交付半成品也不需要危险的递归删除。
- 原二进制模板、截图和旧构建均采用可恢复移动，没有直接销毁；最终 Git 使用全新历史，避免旧提交把已清理材料重新带入演示仓库。

## 一句话亮点

把一套真实业务驾驶舱拆成了“数据全是假的、流程真的能跑”的本地演示产品：三千条订单明细、完整财务链路、十类导出和分级汇报，断网也能讲完整个故事。
