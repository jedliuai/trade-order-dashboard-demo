# 演示仓库复制与改造摸底

## 做了什么

把源项目复制到了当前演示专用文件夹，确认本机 GitHub 登录可用，目标名称 `trade-order-dashboard-demo` 尚未创建。检查了前端数据入口、导出入口、Telegram 汇报实现和项目目录。这一阶段只做复制和摸底，还没有完成脱敏、替换存储、创建新远程仓库或推送。

## 为什么做

准备把实际业务项目拆出一份可以安全展示的独立演示版：保留订单驾驶舱、经营分析、汇报和导出，数据全部虚构并保存在项目本地，不再依赖原来的业务系统和远程基础设施。

## 值得记住的决策、坑和技术点

- 原版并不是一个换掉数据文件就能运行的纯前端：主要数据读取和很多业务写入依赖远程接口，导出和 Telegram 也依赖后台服务。
- 需要清理的不只有客户表。原始业务模板、历史文档、截图、测试样例和旧 Git 历史都要检查，不能直接把这次克隆原样推到演示仓库。
- 建议采用项目内 JSON 文件加一个随应用启动的本地服务，解决浏览器不能自动读写项目目录以及不能安全保存机器人密钥的问题。该方案仍待用户确认。
- 金额、回款、利润和状态流转应保留已有业务口径，不在演示化过程中擅自改变。
- 目前仍是源仓库的浅克隆；后续应在脱敏完成后建立全新的 Git 历史，并绑定新的演示仓库，避免误推源项目。

## 一句话亮点

把真实业务驾驶舱拆成可独立演示的产品，第一步不是换几个客户名，而是找清楚数据、模板和基础设施之间的全部联系。
